# 机械臂首次运动操作指南（电脑端）

日期：2026-10-27。适用环境：Ubuntu 24.04、x86_64、ROS 2 Jazzy、Python 3.12。

本指南先通过底层串口控制夹爪，绕开当前不能加载的 ARM FK/IK 库。以下命令供实际操作时执行；编写本指南时未启动控制节点，也未验证实机通信或动作。

## 1. 当前可运行范围

| 包或程序 | 当前用途与限制 |
|---|---|
| `ros_robot_controller` | 已构建，可用于连接控制板、读取舵机位置、发送位置指令；实机协议尚未验证 |
| `servo_controller` | 可使用关节位置控制，启动时需要关闭 `grasp` |
| `sdk` | 可通过 `enable_kinematics:=false` 启动基础控制链 |
| `kinematics`、自动抓取、分拣 | ARM 运动学库与 x86_64 不兼容，暂不可用 |
| `peripherals` 的手柄控制 | 用户已反馈手柄控制有效；需保留现有可用服务配置。点动调速见第 10 节；本次未重新实测运动 |
| `software/armpi_ultra_control` | 路径已适配，但主界面仍直接导入 FK/IK，尚不能正常使用 |

第一次测试只启动 `ros_robot_controller`。不要同时启动 GUI、另一个底层控制节点或整套 bringup。后者包含自动姿态操作。

给控制板及舵机正常供电，夹爪内不放物体，手离开夹爪，确保机械臂周围有活动空间。

## 2. 终端 A：刷新权限并加载环境

如果当前终端还没有 `dialout` 权限，先执行：

```bash
newgrp dialout
```

进入新 shell 后执行：

```bash
cd /home/lyl/ros2_ws
source scripts/setup_pc.bash

# 应输出 True；仅检查访问权限，不打开串口。
python3 -c 'import os; print(os.access(os.environ["ARMPI_SERIAL_PORT"], os.R_OK | os.W_OK))'
```

`newgrp` 仅影响当前新 shell 及其子进程。注销桌面重新登录可使 IDE 和其他新进程一起刷新组权限。

当前默认配置在 `config/pc.env`：

```text
ARMPI_SERIAL_PORT=/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0
ARMPI_BAUDRATE=1000000
```

这条 by-id 路径来自已枚举到的 CH340 转换器，不代表已经确认其连接的控制板协议。若设备不存在，先查看：

```bash
ls -l /dev/serial/by-id/
```

若实际路径发生变化，在终端 A 中显式设置正确值，再继续：

```bash
# 将下面路径替换为实际控制板连接对应的路径。
export ARMPI_SERIAL_PORT=/dev/serial/by-id/实际设备名称
```

若访问检查仍为 False，先解决设备路径或权限问题，不继续启动。

## 3. 终端 A：启动底层控制节点

```bash
ros2 launch ros_robot_controller ros_robot_controller.launch.py
```

保持终端 A 运行。日志会显示串口与波特率；若出现权限错误、无法打开设备或其他异常，先处理错误。

此节点会真实打开串口。当前构造函数发送 PWM 舵机偏差和电机停止等初始化命令，但没有发送整臂总线舵机初始姿态。因此该启动操作不是纯只读检查。

## 4. 终端 B：读取夹爪位置

当前配置中，舵机 **ID 1** 对应夹爪开合。打开第二个终端：

```bash
cd /home/lyl/ros2_ws
source scripts/setup_pc.bash

ros2 service call /ros_robot_controller/bus_servo/get_state \
  ros_robot_controller_msgs/srv/GetBusServoState \
  "{cmd: [{id: 1, get_id: 1, get_position: 1}]}"
```

观察返回结果中的 `state` 项，重点是：

```text
present_id: [1]
position: [实际位置值]
```

这是读取请求，不包含移动目标。**读取到非空位置后再进行下一步。** 原服务存在无超时等待和失败仍返回 success 的问题，现已修复：重启底层节点后，每个读取项默认最多等待约 1 秒，未收到有效响应时返回 `success=False`。仍应同时核对 `present_id` 和 `position`；已经启动的旧进程需要重启才会使用修复。

如果返回 `position: []`，或服务长时间没有响应，先检查：

- 终端 A 是否正常启动，有无串口异常。
- 控制板与舵机是否供电，USB 转换器是否确实连接该控制板。
- 舵机 ID 与接线、波特率及协议是否匹配。
- 是否有其他 GUI 或节点占用同一个串口。

位置未读到时不要盲目发布目标值。

## 5. 终端 B：首次小幅运动

以刚才读出的实际位置为基准，第一次只增加或减少约 20，避开夹爪已经闭紧或张到限位的方向。位置值使用本机代码中的 0–1000 标度，但实际机械允许范围还应依据夹爪状态确认。

**下面仅是条件示例：只有刚才读到 `position: [500]`，且向 520 运动方向有余量时，才执行此命令。** 如果当前值不是 500，应修改目标值，不要直接照发 520。

```bash
ros2 topic pub --once /ros_robot_controller/bus_servo/set_position \
  ros_robot_controller_msgs/msg/ServosPosition \
  "{duration: 1.0, position: [{id: 1, position: 520}]}"
```

| 字段 | 含义 |
|---|---|
| `id: 1` | 仅控制夹爪舵机 |
| `position: 520` | 绝对目标位置值，不是角度，也不是相对增量 |
| `duration: 1.0` | 运动时间 1 秒 |
| `--once` | 只发布一次 ROS 消息 |

这里使用的是 **`ros_robot_controller_msgs/msg/ServosPosition`**，发布到 `/ros_robot_controller/bus_servo/set_position`；不要与上层 `/servo_controller` 使用的 `servo_controller_msgs/msg/ServosPosition` 混淆。

发布后再次执行第 4 步读取命令，观察位置是否变化，并检查夹爪是否按预期动作。ROS 显示消息已发布不等于硬件已经执行成功。

## 6. 夹爪停止与结束测试

需要发送夹爪停止指令时，在终端 B 执行：

```bash
ros2 topic pub --once /ros_robot_controller/bus_servo/set_state \
  ros_robot_controller_msgs/msg/SetBusServoState \
  "{state: [{present_id: [1, 1], stop: [1]}]}"
```

这里 `present_id: [1, 1]` 是当前状态设置接口使用的 `[有效标志, 舵机ID]` 格式，与读取返回值的表示不同。该指令只停止 ID 1，并非整臂停止或卸力。

软件停止仍依赖节点和串口通信正常。关闭终端或 Ctrl+C 不能保证舵机立即停止，也不等于卸力。测试结束、确认动作完成后，再在终端 A 按 Ctrl+C 结束节点。

## 7. 后续基础控制入口

以下供完成底层通信测试后使用，不要与终端 A 中的同一个底层节点重复启动。

### 方案 A：基础控制链一起启动

先结束第 3 步启动的底层节点，再执行：

```bash
source scripts/setup_pc.bash
ros2 launch sdk armpi_ultra.launch.py enable_kinematics:=false
```

该入口包含底层控制和上层舵机控制，关闭运动学及依赖它的 grasp 节点。它不修复手柄程序中对运动学服务的等待。

### 方案 B：保留底层节点，单独启动上层舵机控制

在底层节点已运行的情况下，另开终端：

```bash
cd /home/lyl/ros2_ws
source scripts/setup_pc.bash
ros2 launch servo_controller servo_controller.launch.py enable_grasp:=false
```

方案 A、B 选其一。第一次夹爪测试不需要启动这些额外节点。

手柄后续修改建议与入口见 [FK_IK资料核对与遥控适配建议.md](FK_IK资料核对与遥控适配建议.md)。当前手柄程序尚不能因关闭运动学节点而自动进入可用的单舵机模式。

## 9. 停在 requester: making request 时

`waiting for service to become available...` 后出现 `requester: making request`，说明服务已经发现，请求已发出；不是仍停在服务发现阶段。若后续长时间无响应，原 SDK 的无超时队列读取可能让回调一直等待。

2026-10-27 已修复总线舵机读取：每项读取默认 1 秒超时，检查回包 ID/命令/长度，失败返回 None；服务返回 `success=False` 并记录具体字段。`get_id` 加 `get_position` 是两项读取，无回复时通常约 2 秒结束，不是整个请求只有 1 秒。此修改不保证供电、串口协议或固件问题已经解决。

在终端 B 按 Ctrl+C 结束旧请求，在终端 A 按 Ctrl+C 结束旧节点，然后重新启动第 3 步。当前使用 symlink 安装，新进程会加载修改后的源码，无需重新构建。若旧节点卡住不能退出，先提供其终端输出排查，避免再启动一个节点争用串口。

重启后可先只读取位置，以减少一项请求：

```bash
ros2 service call /ros_robot_controller/bus_servo/get_state \
  ros_robot_controller_msgs/srv/GetBusServoState \
  "{cmd: [{id: 1, get_position: 1}]}"
```

这个请求不查询 ID，因此 `present_id: []` 是预期的；应检查 `success` 与 `position`。再次动作前以新读数为准，不能沿用历史日志或教程示例位置。


## 10. 手柄点动速度调节（2026-10-27）

用户反馈手柄已能控制机械臂。现已将关节及笛卡尔点动的步长、指令运动时间开放为启动参数，原默认值不变；详细命令、模式说明和回退方式见 [手柄速度调节说明.md](手柄速度调节说明.md)。

关节微调可从 `joint_step:=5 joint_duration:=0.10` 开始，默认分别是 `10` 和 `0.05`。需要松开按键、确认动作完成、结束旧手柄节点后再用新参数重启；不要同时运行两个遥控节点。启动仍会发送初始化姿态，START 仍执行原来的回中动作，它们不会随点动参数减速。先清空活动空间，准备可靠的停止措施。

最初参数化通过 127 项测试；随后电脑 USB 排障修复了原输入回调的无限循环。当前仍不支持在线热改调速参数，也不保证固定角速度或末端速度；完整启动方式见第 11 节。


## 11. USB 手柄接收器移到电脑后的启动（2026-10-27）

电脑已通过 pygame 识别 USB WirelessGamepad。原手柄节点在单关节模式也会等待 FK/IK，且输入回调无限循环阻塞状态更新；现已修复，默认 enable_kinematics=false。应先启动底层驱动和 servo_controller，再启动手柄；仅启动 peripherals 的 launch 不会自动补齐这些节点。

按 [电脑USB手柄控制排障与启动.md](电脑USB手柄控制排障与启动.md) 执行只读输入验证、串口权限检查及两终端启动。注意手柄节点启动会发送原初始化姿态，先清空活动空间；不支持长按自动重复，先短按测试。146 项离线用例通过，已构建 peripherals；实机点动仍待用户验证。
